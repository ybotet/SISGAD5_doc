# 17. Администрирование базы данных (PostgreSQL)
_(Administración de base de datos - PostgreSQL)_

---

## 17.1. Введение
_(Introducción)_

В данной практической работе описываются процедуры администрирования базы данных PostgreSQL для корпоративной системы. Определены роли и права доступа, стратегия резервного копирования, мониторинг, оптимизация запросов и регламент обслуживания.

_(En esta práctica se describen los procedimientos de administración de la base de datos PostgreSQL para el sistema corporativo. Se definen roles y permisos, estrategia de respaldo, monitoreo, optimización de consultas y plan de mantenimiento.)_

### 17.3.3. Модель угроз и меры снижения риска
_(Modelo de amenazas y medidas de mitigación)_

| Угроза _(Amenaza)_         | Мера снижения _(Mitigación)_                   |
| -------------------------- | ---------------------------------------------- |
| Несанкционированный доступ | Ограничение IP в `pg_hba.conf`, сложные пароли |
| Перехват трафика           | TLS/SSL шифрование                             |
| Атака на пароль            | Хранение паролей в Vault, регулярная смена     |

| Утечка данных              | Шифрование бэкапов, аудит доступа              |

## 17.4. Создание ролей и прав доступа
_(Creación de roles y permisos)_

### 17.4.1. Роли базы данных
_(Roles de base de datos)_

| Роль _(Rol)_    | Назначение _(Propósito)_ |
| --------------- | ------------------------ |
| `app_user`      | Приложение (Node.js)     |
| `readonly_user` | Только чтение (отчеты)   |
| `admin_user`    | Администрирование БД     |
| `auditor_user`  | Аудит (таблицы Audit)    |

### 17.4.2. SQL скрипт создания ролей
_(Script SQL de creación de roles)_

```sql
-- Создание ролей
CREATE ROLE app_user WITH LOGIN PASSWORD 'secure_app_password';
CREATE ROLE readonly_user WITH LOGIN PASSWORD 'secure_readonly_password';
CREATE ROLE admin_user WITH SUPERUSER LOGIN PASSWORD 'secure_admin_password';
CREATE ROLE auditor_user WITH LOGIN PASSWORD 'secure_auditor_password';

-- Назначение прав
-- app_user: полный CRUD
GRANT CONNECT ON DATABASE bd_mp TO app_user;
GRANT CONNECT ON DATABASE bd_users TO app_user;
GRANT CONNECT ON DATABASE bd_materiales TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_user;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_user;

-- readonly_user: только чтение
GRANT CONNECT ON DATABASE bd_mp TO readonly_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_user;

-- auditor_user: чтение таблиц аудита
GRANT CONNECT ON DATABASE bd_users TO auditor_user;
GRANT SELECT ON Audit, AccionUsuario, UserSession TO auditor_user;

-- admin_user: имеет все права (через SUPERUSER)
```

> В production среде приложение (Node.js) использует **только одну роль** — `app_user`. Остальные роли (`readonly_user`, `admin_user`, `auditor_user`) предназначены для административных задач, отчетов и аудита, но не используются непосредственно приложением.

_(En el entorno de producción, la aplicación (Node.js) utiliza **solo un rol** — `app_user`. Los demás roles son para tareas administrativas, reportes y auditoría, pero no los utiliza directamente la aplicación.)_

### 17.4.3. Политика смены паролей
_(Política de cambio de contraseñas)_

| Роль            | Периодичность смены | Хранение                     |
| --------------- | ------------------- | ---------------------------- |
| `app_user`      | Каждые 90 дней      | Vault / Переменные окружения |
| `readonly_user` | Каждые 90 дней      | Vault                        |
| `admin_user`    | Каждые 60 дней      | Vault + менеджер паролей     |
| `auditor_user`  | Каждые 90 дней      | Vault                        |

## 17.6. Резервное копирование, стратегия и регламент
_(Respaldo, estrategia y procedimiento)_

### 17.6.1. Стратегия резервного копирования
_(Estrategia de respaldo)_

| Тип бэкапа _(Tipo)_     | Периодичность _(Frecuencia)_ | Время выполнения _(Horario)_ | Хранение _(Retención)_ |
| ----------------------- | ---------------------------- | ---------------------------- | ---------------------- |
| Полный (pg_dump)        | Ежедневно                    | 02:00                        | 30 дней                |
| Инкрементальный (WAL)   | Каждый час                   | :00 каждого часа             | 7 дней                 |
| Логический (pg_dumpall) | Еженедельно                  | Воскресенье 03:00            | 90 дней                |

### 17.6.2. Скрипт резервного копирования
_(Script de respaldo)_

```bash
#!/bin/bash
# backup.sh

DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR="/backup/db"
DB_NAME="bd_mp"

# Полный бэкап
pg_dump -U admin_user -d $DB_NAME -F c -f "$BACKUP_DIR/${DB_NAME}_full_$DATE.dump"

# Копирование WAL файлов
cp /var/lib/postgresql/15/main/pg_wal/* "$BACKUP_DIR/wal/"

# Удаление старых бэкапов (старше 30 дней)
find $BACKUP_DIR -name "*.dump" -mtime +30 -delete

# Отправка уведомления об успешном бэкапе
echo "Backup completed: ${DB_NAME}_full_$DATE.dump" | mail -s "DB Backup" admin@empresa.com
```

### 17.6.3. Место хранения и требования к доступу
_(Ubicación de almacenamiento y requisitos de acceso)_

| Аспект _(Aspecto)_ | Требование _(Requisito)_             |
| ------------------ | ------------------------------------ |
| Локация            | Отдельный сервер / Сетевое хранилище |
| Шифрование         | AES-256 для бэкапов на диске         |
| Доступ             | Только `admin_user`                  |
| Срок хранения      | 30 дней (full), 7 дней (WAL)         |

## 17.7. Проверка восстановления из бэкапа
_(Verificación de restauración desde respaldo)_

### 17.7.1. Протокол восстановления
_(Protocolo de restauración)_

```bash
# 1. Остановить приложение (если работает)
# 2. Создать новую пустую базу данных
createdb -U admin_user bd_mp_restore

# 3. Восстановить из полного бэкапа
pg_restore -U admin_user -d bd_mp_restore /backup/db/bd_mp_full_20240101_020000.dump

# 4. Применить WAL файлы (для PITR)
# Скопировать WAL файлы в каталог восстановления
cp /backup/wal/* /var/lib/postgresql/15/main/pg_wal/

# 5. Запустить PostgreSQL
sudo systemctl start postgresql

# 6. Проверить целостность данных
psql -U admin_user -d bd_mp_restore -c "SELECT COUNT(*) FROM Ticket;"
```

### 17.7.2. Критерии успешного восстановления
_(Criterios de restauración exitosa)_

| Проверка _(Verificación)_ | Критерий _(Criterio)_             |
| ------------------------- | --------------------------------- |
| Целостность данных        | Все таблицы успешно восстановлены |
| Количество записей        | COUNT(*) соответствует ожидаемому |
| Внешние ключи             | Нет ошибок FK                     |
| Время восстановления      | < 1 часа для полной БД            |

## 17.8. Мониторинг и показатели состояния
_(Monitoreo y métricas de estado)_

### 17.8.1. Метрики для мониторинга
_(Métricas para monitoreo)_

| Метрика _(Métrica)_ | Описание _(Descripción)_                 | Порог тревоги _(Umbral)_   |
| ------------------- | ---------------------------------------- | -------------------------- |
| Активные соединения | `SELECT count(*) FROM pg_stat_activity;` | > 80% от `max_connections` |
| CPU загрузка        | Нагрузка на процессор                    | > 80%                      |
| IOPS                | Операции ввода/вывода                    | > 1000                     |
| Задержка запросов   | Время выполнения                         | > 2 секунд                 |
| Размер БД           | Общий размер базы                        | > 90% диска                |
| Блокировки (locks)  | Количество ожидающих блокировок          | > 10                       |

### 17.8.2. Запросы для сбора метрик
_(Consultas para recopilar métricas)_

```sql
-- Активные соединения
SELECT count(*) FROM pg_stat_activity WHERE state = 'active';

-- Размер базы данных
SELECT pg_database_size('bd_mp') / 1024 / 1024 AS size_mb;

-- Медленные запросы (pg_stat_statements)
SELECT query, calls, total_time, mean_time 
FROM pg_stat_statements 
ORDER BY mean_time DESC 
LIMIT 10;

-- Текущие блокировки
SELECT 
    locktype,
    relation::regclass,
    mode,
    granted,
    pid,
    query
FROM pg_locks
JOIN pg_stat_activity ON pg_locks.pid = pg_stat_activity.pid
WHERE NOT granted;
```

## 17.9. Оптимизация типовых запросов и индексация
_(Optimización de consultas típicas e indexación)_

### 17.9.1. Типовые запросы (3-5 запросов)
_(Consultas típicas - 3-5 consultas)_

#### Запрос 1: Получение открытых заявок
_(Consulta 1: Obtener tickets abiertos)_

```sql
SELECT t.id, t.descripcion, t.estado, t.prioridad, c.nombre as cliente
FROM Ticket t
JOIN Cliente c ON t.clienteId = c.id
WHERE t.estado IN ('Открыта', 'Назначена', 'Проверена')
ORDER BY t.prioridad DESC, t.fechaCreacion ASC;
```

**Индекс:**

```sql
CREATE INDEX idx_ticket_estado_prioridad_fecha ON Ticket(estado, prioridad DESC, fechaCreacion);
```

#### Запрос 2: История заявок по клиенту
_(Consulta 2: Historial de tickets por cliente)_

```sql
SELECT t.id, t.estado, t.fechaCreacion, t.fechaCierre
FROM Ticket t
WHERE t.clienteId = 123
ORDER BY t.fechaCreacion DESC;
```

**Индекс:**

```sql
CREATE INDEX idx_ticket_cliente_fecha ON Ticket(clienteId, fechaCreacion DESC);
```

#### Запрос 3: Активные назначения техника
_(Consulta 3: Asignaciones activas de un técnico)_

```sql
SELECT COUNT(*) 
FROM Asignacion a
JOIN Ticket t ON a.ticketId = t.id
WHERE a.trabajadorId = 5 
  AND t.estado NOT IN ('Закрыта', 'Решена');
```

**Индекс:**

```sql
CREATE INDEX idx_asignacion_ticket_estado ON Asignacion(trabajadorId, ticketId);
CREATE INDEX idx_ticket_estado ON Ticket(estado);
```

#### Запрос 4: Отчет по материалам
_(Consulta 4: Reporte de materiales)_

```sql
SELECT m.codigo, m.nombre, SUM(c.cantidad) as total_consumido
FROM Material m
JOIN Consumo c ON m.id = c.materialId
WHERE c.fecha BETWEEN '2024-01-01' AND '2024-12-31'
GROUP BY m.id
ORDER BY total_consumido DESC;
```

**Índice:**

```sql
CREATE INDEX idx_consumo_fecha ON Consumo(fecha);
CREATE INDEX idx_consumo_material ON Consumo(materialId);
```

#### Запрос 5: Поиск по ключу (clave)
_(Consulta 5: Búsqueda por clave)_

```sql
SELECT * FROM Consumo 
WHERE clave = '7R' 
AND fecha > NOW() - INTERVAL '30 days';
```

**Índice:**

```sql
CREATE INDEX idx_consumo_clave_fecha ON Consumo(clave, fecha);
```

### 17.9.2. Анализ планов выполнения

## 17.10. Регламент обслуживания и профилактики
_(Plan de mantenimiento y prevención)_

### 17.10.1. Процедуры обслуживания
_(Procedimientos de mantenimiento)_

| Процедура _(Procedimiento)_ | Периодичность _(Frecuencia)_ | SQL команда                         |
| --------------------------- | ---------------------------- | ----------------------------------- |
| `VACUUM`                    | Ежедневно                    | `VACUUM (VERBOSE, ANALYZE) Ticket;` |
| `ANALYZE`                   | Ежедневно                    | `ANALYZE Ticket;`                   |
| `REINDEX`                   | Еженедельно                  | `REINDEX TABLE Ticket;`             |
| Обновление статистики       | Ежедневно                    | `ANALYZE;`                          |

### 17.10.2. Скрипт обслуживания
_(Script de mantenimiento)_

```sql
-- maintenance.sql
-- Запускать ежедневно в 03:00

-- 1. VACUUM (очистка мертвых строк)
VACUUM (VERBOSE, ANALYZE) Ticket;
VACUUM (VERBOSE, ANALYZE) Asignacion;
VACUUM (VERBOSE, ANALYZE) Consumo;

-- 2. Обновление статистики для оптимизатора
ANALYZE;

-- 3. Логирование размера таблиц
SELECT 
    relname AS table_name,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

### 17.10.3. Проверка результатов обслуживания
_(Verificación de resultados del mantenimiento)_

```sql
-- Проверка мертвых строк после VACUUM
SELECT 
    relname AS table_name,
    n_dead_tup AS dead_rows,
    n_live_tup AS live_rows
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

-- Проверка фрагментации индексов
SELECT 
    schemaname,
    tablename,
    indexname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan;
```
